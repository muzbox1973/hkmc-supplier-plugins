# /eight-d-report

> 낯선 자리표시자나 연결된 도구는 [CONNECTORS.md](../../CONNECTORS.md)에서 확인한다.

고객이 **받아들일 수 있는** 8D를 만든다. 핵심은 발생 원인과 유출 원인을 따로 밝히고, 대책이 그 원인을 정확히 막는다는 것을 증빙으로 보여 주는 것이다.

## 필요한 정보

- 불량 현상(사진, 수량, 품번, LOT, 발견 장소: 고객 라인·필드·사내)
- 통보 일자와 고객 요구 회신 기한
- 해당 공정의 작업표준서·관리계획서·PFMEA(있으면)
- 이미 조사한 내용

정보가 부족해도 초안을 먼저 만들고, 빈칸은 `[확인 필요: …]`로 표시한다. 없는 사실을 만들어 채우지 않는다.

## 8D 구성과 작성 기준

| 단계 | 작성 기준 |
|---|---|
| D0 긴급 대응 | 고객 라인 정지 위험 판단, 대체품 긴급 납품 여부 |
| D1 팀 구성 | 품질·생산·생산기술·(필요 시)개발·구매, 팀장 명시 |
| D2 문제 정의 | 5W2H와 Is/Is-not으로 범위 확정. "불량 발생"이 아니라 "○○ 품번 ○○ 공정에서 ○○ 현상 ○개" 수준 |
| D3 봉쇄 조치 | 고객 재고·운송 중·사내 완제품·재공품·원자재까지 선별 범위와 결과 수량, 선별 기준, **클린 포인트**(대책 적용 첫 LOT 식별 표시) |
| D4 근본원인 | **발생 원인**과 **유출 원인**을 각각 5Why로 분석. 특성요인도는 4M1E(사람·설비·재료·방법·측정/환경). 재현 시험 또는 데이터로 원인 검증 |
| D5 영구 대책 | 원인별 대책 1:1 매칭. 사람 주의 대책("교육 강화")만으로 끝내지 않고 오류방지·설비·검사 방식 개선을 우선 |
| D6 대책 적용·효과 확인 | 적용일, 적용 LOT, 효과 확인 기간과 데이터(불량률 전후 비교) |
| D7 재발 방지·수평 전개 | PFMEA·관리계획서·작업표준서 개정, 유사 품번·유사 공정·타 사업장 전개 |
| D8 종결 | 팀 공유, 고객 승인 요청 |

## 검토 모드

사용자가 이미 쓴 8D를 주면 아래로 점검하고 고칠 문장을 제안한다.
- 문제 정의가 측정 가능한가
- 봉쇄 범위에 운송 중 재고와 고객 재고가 빠지지 않았는가
- 근본원인이 "작업자 부주의"에서 멈추지 않았는가 (왜 실수가 가능했는가까지)
- 유출 원인을 따로 분석했는가
- 대책과 원인이 1:1로 연결되는가
- 효과 확인에 숫자 데이터가 있는가
- 문서 개정(PFMEA·관리계획서·작업표준서)이 포함되었는가

## 출력 형식

```markdown
# 8D 개선대책서
| 항목 | 내용 |
|---|---|
| 고객사 / 품번 / 품명 | |
| 불량 현상 | |
| 발생 장소 / 수량 / LOT | |
| 통보일 / 회신 기한 | |
| 작성 / 승인 | |

## D1 팀 구성
## D2 문제 정의 (5W2H, Is/Is-not)
## D3 봉쇄 조치 (선별 범위·수량·결과, 클린 포인트)
## D4 근본원인
### 발생 원인 (5Why)
### 유출 원인 (5Why)
### 원인 검증
## D5 영구 대책 (원인 ↔ 대책 대응표)
## D6 적용 및 효과 확인
## D7 재발 방지 (문서 개정, 수평 전개)
## D8 종결
```

고객사가 지정한 양식이 첨부되면 그 양식의 항목 순서와 용어를 그대로 따른다.

## 연결 도구가 있으면

- **~~MES**: 해당 LOT의 생산 일시·설비·작업자·검사 기록을 조회해 D2·D4 근거로 쓴다.
- **~~customer portal**: 클레임 통보 내용과 회신 기한을 확인한다.
- **~~groupware**: 완료된 8D를 내부 결재용 기안문으로 바꾼다.

## 팁

- 고객 회신은 보통 "봉쇄 조치 결과(초동)"와 "최종 8D" 두 번에 나뉜다. 기한이 짧으면 D3까지 먼저 회신하는 초동 보고서를 제안한다.
- 같은 불량이 반복이면 이전 8D의 대책이 왜 효과가 없었는지를 D4에 반드시 넣는다.
